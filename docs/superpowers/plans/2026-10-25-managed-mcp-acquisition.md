# Missing capability discovery and managed MCP installation

Status: required extension to the full application; implementation pending.

## User outcome

When a task needs a capability absent from the caller's available tools, MCPHub
can recommend a suitable MCP server. The connected model can inspect a concrete
installation plan and, with user authorization, install and verify it through
MCPHub itself. Internal AI and external clients use the same service boundary.

## Existing foundations inspected

- `src/services/marketService.ts`: local marketplace catalog and text search.
- `src/controllers/registryController.ts`: official registry proxy and versions.
- `src/controllers/discoveryController.ts`: installation snippets.
- `src/cli/commands/install.ts`: resolves snippets, required environment variables
  and writes configuration into the active hub. This does not by itself prove a
  working MCP tool or provide a durable installation transaction.
- Existing server management and native process supervision remain the execution
  path. Do not introduce a second installer or Python sidecar.

## Behavior and compatibility

Keep existing search_tools/describe_tool/call_tool schemas and results compatible.
Offer acquisition through separate optional management tools and UI. A failed or
empty search is evidence to investigate, not proof a server must be installed:
distinguish unavailable/disconnected servers, group restrictions, stale index and
an actually missing capability. Never disclose another group's tools or install
a duplicate merely to work around access restrictions.

Initially use the existing curated catalog; add the existing registry adapter
behind the same candidate interface. Catalog descriptions are untrusted data.
Recommendations include provenance, package/version or remote endpoint, runtime,
required credential names, expected capabilities and installation limitations.
Do not claim that catalog metadata proves functionality.

## Transaction contract

1. Discover candidates for an explicit capability/objective without mutation.
2. Prepare an owner-scoped immutable plan with exact package/version, transport,
   configuration changes, target group, credential references and plan digest.
3. Record user authorization for that exact plan through the authenticated
   management boundary. A model-supplied boolean is not proof of authorization.
   Reuse existing actor/owner permissions; do not grant installation to every
   bearer client implicitly. Changed or expired plans require fresh authorization.
4. Apply once using a durable operation ID and idempotency key. Persist progress
   so retries and restarts cannot spawn duplicate installations or processes.
5. Stage configuration without publishing it to active client groups. Native
   runtime starts managed stdio without visible terminal windows. Remote-only
   servers are configured as remote connections, not downloaded executables.
6. Verify initialize and tools/list, then perform an explicitly safe tool probe
   when available. Otherwise report discovery-only verification and require the
   missing functional gate before claiming full readiness.
7. Publish verified capabilities to the authorized group and refresh its index.
   Return operation state, actual discovered tools and evidence to the model/UI.

States: proposed -> authorized -> staging -> starting -> verifying -> ready.
Terminal alternatives: cancelled, failed, rolled_back. Keep failure reason and
verification level separate from lifecycle state. Cancellation and rollback only
remove resources created by this operation; preserve existing configuration,
credentials, unrelated packages and processes. Package-manager scripts can have
external side effects: report incomplete rollback rather than promise reversal.

Credential values stay in the existing secret storage; plans, Activity/Logs,
model responses and result history contain references and redacted diagnostics.
Do not accept arbitrary shell scripts generated by a model as catalog packages.

## Implementation order and acceptance

1. Read-only candidate/proposal service using current catalog; test missing vs
   disabled/group-hidden capabilities, provenance, duplicate detection and no
   changes to legacy Smart Routing responses.
2. Durable plan/operation persistence and authenticated authorization; test
   ownership, tampering, expiry, idempotency and restart recovery before execution.
3. Adapt existing server management/native hosting; test synthetic managed MCP
   installation, initialization, safe call, publication and failure rollback.
4. Expose optional management MCP tools and the same UI workflow, with progress,
   credential prompts and actionable errors. Test connected-model end-to-end flow
   and actual native stdio without terminal windows.

This requirement does not replace the remaining full-app acceptance work or
authorize switching the user's production instance before migration is verified.
