---
title: "Tool Result History"
description: "Inspect immutable MCP tool execution results and retrieval metrics."
---

Tool Result History is available in database mode. Dashboard history endpoints are restricted to administrators; the agent-facing MCP operations below are restricted to the authenticated owner's currently accessible results. Each successfully persisted eligible tool execution receives a `result_id`. A storage failure does not fail or repeat the upstream tool call. Retention maintenance failure preserves an already saved result ID and is retried on the next capture. The original MCP response is stored as immutable RAW before optional legacy compression; pin and usage counters are stored separately.

## Agent-facing MCP memory

### Opt-in objective-aware execution

`call_tool` accepts an optional `smart` object, separate from backend arguments:

```json
{"toolName":"server-read_logs","arguments":{},
 "smart":{"retrieve":true,"objective":"Find GPU Xid 79 and PCIe failures","maxOutputTokens":3000}}
```

The objective may fall back to the existing top-level `objective` field. It is
limited to 2,000 characters; output budget is 512–4,096 estimated cl100k tokens.
The default remains disabled. The initial execution path uses BM25 lexical
windows and exact diagnostic identifiers, not semantic vector reranking.

RAW capture happens first. Only a successfully captured, retained payload can
produce a fragment response; a result ID supplied by an upstream is insufficient.
Invalid opt-in settings are rejected before invoking the backend tool.
Results at or below 8,000 estimated tokens, missing useful
hits, metadata-only capture, failed storage or retrieval failures retain the
original response. Explicit retrieval bypasses legacy lossy compression.

Fragment responses are labeled `original-fragments`, preserve `isError` and the
saved result ID, and fit the requested estimated token budget including their
metadata. Each fragment identifies its original `content` block and end-exclusive
UTF-16 text offsets. Text is copied exactly, including line endings; it is not a
summary. Read the complete stored MCP envelope with `get_tool_result` or ranges.
These provisional thresholds still require workload benchmarks; this lexical
path does not claim complete hybrid retrieval.

Administrators can set `smartRouting.resultRetrieval` through the existing
system-config API, without a database schema migration:

```json
{"smartRouting":{"resultRetrieval":{"minTokens":8000,"maxOutputTokens":3000,
 "policies":{"desktop-commander/*":{"minTokens":12000},
 "basic-memory/read_content":{"mode":"passthrough"}}}}}
```

Defaults, `server/*`, bare tool name, then `server/tool` are merged in that order.
Rules accept `mode` (`fragments` or `passthrough`), `minTokens` (512–1,000,000)
and `maxOutputTokens` (512–4,096). A configured budget caps the caller's budget;
`passthrough` overrides caller opt-in. Unknown or unreadable policies preserve
the full response. Policies do not automatically enable retrieval: the call
must still opt in. Sending an empty object clears configured defaults and rules.
The policy editor in the dashboard remains pending.

When database history is available, `$smart` routes expose these additional tools:

| Tool | Arguments | Result |
| --- | --- | --- |
| `get_tool_result` | `result_id` | Exact stored RAW, up to 65,536 UTF-8 bytes |
| `get_tool_result_range` | `result_id`, `start`, `end` | End-exclusive byte range, base64 encoded, with offsets, total bytes and RAW digest |
| `search_tool_result` | `result_id`, `query`, optional `limit` | Matching indexed chunks within one result |
| `search_tool_results` | `query`, optional `filters`, optional `limit` | Matching history metadata, without RAW |
| `pin_tool_result` | `result_id` | Protect the result from automatic retention |
| `unpin_tool_result` | `result_id` | Remove retention protection |

These operations read existing evidence; they do not rerun the source tool. The caller's authenticated username and key, when present, must match the stored result. Current group, server and tool visibility also applies. Missing identity is rejected, and tool arguments cannot supply another owner or key. Dashboard administrator access does not bypass these MCP ownership checks.

Search queries contain 1–2,000 characters and `limit` is an integer from 1 to 20 (default 10). History filters accept `server`, `tool`, `status`, `sessionId`, `conversationId`, `modelId`, `taskId`, `traceId` and `branchId`. Search responses are bounded to 65,536 bytes; `partial: true` means additional hits were omitted to meet that bound. Embedding failures use lexical retrieval. Search chunks are derived text, not a replacement for exact RAW.

Oversized full reads return an error containing `raw_bytes`, `max_read_bytes` and `next_tool: "get_tool_result_range"`. Request consecutive ranges of at most 65,536 bytes. Decode and concatenate the base64 bytes before decoding UTF-8: a range may cut through a multibyte character. Metadata-only capture policies do not expose RAW through these operations. Pinning changes retention state, not the immutable payload.

All endpoints below are under `/api` and use the normal dashboard authentication.

## Availability and listing

```http
GET /api/tool-results/available
GET /api/tool-results?page=1&limit=20&server=desktop-commander&status=error
```

List filters include `server`, `tool`, `status`, `sessionId`, `conversationId`, `pinned`, `startDate`, and `endDate`. Attribution filters also include `modelId`, `taskId`, `traceId`, and `branchId`. Invalid dates or a start date after the end date return `400` before retrieval. The list response omits RAW content and includes pagination metadata.

## Search and retrieval

```http
GET /api/tool-results/search?q=failed+deployment&limit=20
GET /api/tool-results/:resultId
GET /api/tool-results/:resultId/raw
GET /api/tool-results/:resultId/range?start=0&end=4096
GET /api/tool-results/:resultId/chunks
GET /api/tool-results/:resultId/search?q=Xid+79&limit=10
POST /api/tool-results/reindex
```

Search uses hybrid vector plus PostgreSQL full-text retrieval when the vector path is available and falls back to lexical search when it is not. The response exposes `meta.mode`, `resultCount`, and how many returned hits have lexical, vector, or fused ranks. The range endpoint returns UTF-8 bytes with `206 Partial Content`, `Accept-Ranges`, and `Content-Range` headers.

RAW is never returned by list, search, or metadata endpoints. Metadata-only records return `409` from RAW endpoints with the configured omission reason.
The result-scoped search endpoint searches indexed original chunks and returns retrieval scores without rewriting or exposing the full RAW payload.
Newly captured text includes structured MCP output as well as text blocks. Lexical chunks cover the complete result text; vector embedding input remains bounded to 64,000 UTF-16 units per result, so later chunks may be lexical-only. Chunk boundaries preserve line endings and Unicode characters.

The chunks endpoint returns the exact indexed chunk text with chunk version, byte size, and embedding availability/dimensions. It does not mutate or rewrite immutable RAW.
The reindex endpoint accepts `{ "limit": 25, "onlyMissing": true }` and rebuilds derived chunk/vector rows from existing immutable RAW. It never updates or replaces the stored result payload. Chunk replacement is one atomic database statement: if a new chunk is rejected, the previous complete index remains intact. A pass returns `nextCursor` when more candidates remain. Send it as `afterResultId` on the next request with the same `onlyMissing` setting. This also permits full rebuilds (`onlyMissing: false`) to continue beyond the first batch. `remaining` counts eligible records after the cursor; concurrent new results are not a fixed snapshot, so start another pass if needed.

## Sessions, lineage, pinning, and comparison

```http
GET /api/tool-results/timeline/:sessionId?page=1&limit=100
GET /api/tool-results/conversation-timeline/:conversationId?page=1&limit=100
GET /api/tool-results/:resultId/lineage
POST /api/tool-results/compare
PATCH /api/tool-results/:resultId/pin
```

Both timeline endpoints accept `page` (default 1) and `limit` (default 100, maximum 500). Pagination reports the actual total and page count without duplicating RAW records.

Comparison accepts two to ten `resultIds`:

```json
{ "resultIds": ["9c4…", "b72…"] }
```

Pinning accepts `{ "pinned": true }` or `{ "pinned": false }`. Tool calls may provide `x-conversation-id` and `x-mcphub-parent-result-id` headers to preserve conversation and parent-result lineage.

## Metrics

```http
GET /api/tool-results/stats?server=desktop-commander
```

Stats include total records, pinned records, RAW availability, storage bytes, oldest/newest timestamps, and retrieval counters for hybrid searches, lexical fallbacks, and index failures.
