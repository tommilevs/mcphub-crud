---
title: LoopGuard
description: Conservative advice for repeated identical tool failures
---

The initial deterministic LoopGuard is opt-in with
`MCPHUB_LOOP_GUARD_ENABLED=true`. It requires enabled attribution, a known trace
and branch, and saved Tool Result History. It never blocks, replays or executes
tools. There is no internal LLM call in this first implementation.
You can also enable it in Smart Routing settings and exclude exact tools using
one `server/tool` per line (up to 100 entries). An excluded tool suppresses
both a direct repeat warning and a cycle containing that tool. Environment
variables override saved settings; `MCPHUB_LOOP_GUARD_IGNORED_TOOLS` accepts a
comma-separated exclusion list. Exclusions affect advice only, not execution.

After a failed execution, the hub compares the current result with up to five preceding
results in the same authenticated username/key, trace and branch. Advice is
issued only when all three are failures with the same server, tool, serialized
arguments and RAW digest, and each consecutive gap is less than ten seconds.
Changed outputs, successful calls, pagination/cursor arguments, polling/status/wait
tools and retries separated by at least ten seconds are excluded.
It also detects a six-call A→B→A→B→A→B failure cycle when each corresponding step
has the same tool, arguments and output digest. A successful intermediate step,
changed evidence or backoff in either side suppresses this signal.

Advice links the three original result IDs, is stored in mutable result state,
and is returned in `_meta["dev.mcphub/loopguard"]`. RAW remains unchanged. The
result-detail page displays the advice and evidence links. Telemetry failures
leave the execution result untouched. Ordinary result retention also removes
the associated advice.

Administrators can mark advice Helpful, False positive or Skipped in result
details. `POST /api/tool-results/:id/loopguard-feedback` accepts `verdict` as
`helpful`, `false_positive` or `ignored`. Each submission appends a reviewer/time
observation; the latest submitted observation is also shown with result state.
Feedback cannot create advice on an unrelated result, change RAW or tool
permissions, suppress future executions, or label task success. These observations
are evidence for later evaluation, not automatic training preferences.

These are observations of repeated technical failures, not verified task failures
or training labels. Intentional repeats can still occur and remain permitted.
Unchanged successful states, per-tool retry policies,
automatic agent-reaction tracking and optional ToolPilot reasoning escalation are
subsequent parts of the broader ToolPilot design, not completed features here.
