---
title: LoopGuard
description: Conservative advice for repeated identical tool failures
---

The initial deterministic LoopGuard is opt-in with
`MCPHUB_LOOP_GUARD_ENABLED=true`. It requires enabled attribution, a known trace
and branch, and saved Tool Result History. It never blocks, replays or executes
tools. Optional internal reasoning is disabled by default (configuration below).

An agent may declare an intentional repeat on a particular Smart call:
`hub_context: { trace_key: "k_RETURNED_KEY", repeat_intent: "retry" }`.
Allowed intentions are `poll`, `pagination`, `wait` and `retry`. The intention is
recorded only in that call's attribution, never inherited by later calls or sent
to the upstream tool. Such a call suppresses LoopGuard signals that would use it
as evidence. This declaration grants no permissions and does not establish success.

You can also enable it in Smart Routing settings and exclude exact tools using
one `server/tool` per line (up to 100 entries). An excluded tool suppresses
both a direct repeat warning and a cycle containing that tool. Environment
variables override saved settings; `MCPHUB_LOOP_GUARD_IGNORED_TOOLS` accepts a
comma-separated exclusion list. Exclusions affect advice only, not execution.

The repetition threshold defaults to three, configurable from 3 to 100 in settings
or `MCPHUB_LOOP_GUARD_REPETITIONS`. Exact `server/tool` budget overrides can be
added in settings (`smartRouting.loopGuardToolBudgets`, at most 100 entries).
Cycles honor the larger threshold of both tools. Exclusions still take precedence.
After a failed execution, the hub compares the current result with bounded preceding
results in the same authenticated username/key, trace and branch. Advice is
issued only when the threshold is met by failures with the same server, tool, serialized
arguments and RAW digest, and each consecutive gap is less than ten seconds.
Changed outputs, successful calls, pagination/cursor arguments, polling/status/wait
tools and retries separated by at least ten seconds are excluded.
It also detects A→B failure cycles repeated to the configured threshold when each corresponding step
has the same tool, arguments and output digest. A successful intermediate step,
changed evidence or backoff in either side suppresses this signal.

Advice links the original result IDs, is stored in mutable result state,
and is returned in `_meta["dev.mcphub/loopguard"]`. RAW remains unchanged. The
result-detail page displays the advice and evidence links. Telemetry failures
leave the execution result untouched. Ordinary result retention also removes
the associated advice.

Administrators can mark advice Helpful, False positive or Skipped in result
details. `POST /api/tool-results/:id/loopguard-feedback` accepts `verdict` as
`helpful`, `false_positive` or `ignored`. Each submission appends a reviewer/time
observation; the latest submitted observation is also shown with result state.
Feedback cannot create advice on an unrelated result, change RAW or tool
permissions, suppress future executions, or label task success. These observations
are evidence for later evaluation, not automatic training preferences.

`GET /api/loopguard/summary?days=30` (admin, 1–3650 days) summarizes retained
warnings and their latest reviews. The reported false-positive fraction uses only
Helpful/False positive assessments; ignored and unreviewed warnings are excluded.
No assessments produces `null`, not zero accuracy. Historical votes do not inflate
the number of reviewed warnings.

An agent can explicitly report a reaction on its next Smart call:

```json
{"hub_context":{"trace_key":"k_RETURNED_KEY","loopguard_reaction":{
  "result_id":"WARNING_RESULT_UUID","action":"changed_strategy"
}}}
```

Allowed actions: `accepted`, `declined`, `changed_strategy`, `intentional_retry`.
The warning must exist in the resolved task trace and branch. Reactions are
audited by call/context/model segment, deduplicated by call ID, and removed with
the warning's result. The field is stripped before upstream execution. Storage
failure never blocks or replays the call. Summary/UI labels these as **self-reported**
reactions, not verified behavior, success, or training outcomes. One warning may
have multiple reports. A reaction grants no permissions and does not suppress
future advice; deliberate-repeat intent remains a separate call-local field.

These are observations of repeated technical failures, not verified task failures
or training labels. Intentional repeats can still occur and remain permitted.
Unchanged successful states, independently verified agent behavior/outcomes,
and richer reviewed task/error context for reasoning are
subsequent parts of the broader ToolPilot design, not completed features here.

## Optional internal ToolPilot

Explicitly configure `MCPHUB_TOOLPILOT_ENABLED=true`, `MCPHUB_TOOLPILOT_BASE_URL`
(OpenAI-compatible endpoint), `MCPHUB_TOOLPILOT_MODEL` and, if required,
`MCPHUB_TOOLPILOT_API_KEY` in the runtime environment. This is a **separate**
internal model configuration; it does not borrow the embedding provider or change
the caller's model segment. Keep credentials outside project files.

Only a deterministic LoopGuard warning triggers reasoning. Requests contain the
trigger, count and bounded server/tool names, never RAW, arguments, task text or
trace keys. The returned suggestion is therefore explicitly metadata-only and
unverified. No tools or execution callbacks are provided to the model. Advice is
stored with the warning and shown in result details under `internal_toolpilot`,
alongside configured and provider-reported model identity. It is not attributed
to the user's agent or treated as training truth.

Calls have a three-second timeout, no automatic provider retries, a four-request
concurrency ceiling, and a one-minute per-branch cooldown (including failures).
Cooldown bookkeeping is bounded to 1000 branches per process. Failed or empty
responses leave the deterministic warning intact. The current HTTP execution
response may wait up to the configured client timeout for optional advice.
