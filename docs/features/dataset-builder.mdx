title: Dataset Builder
description: Reviewed, tenant-scoped tool-selection SFT export

Operators may opt into `MCPHUB_CAPTURE_DISCOVERY_CATALOGUE=true` to retain complete
original `search_tools` catalogues alongside discovery fingerprints. Default off:
schemas and descriptions can contain private defaults or service details. Capture
is limited to 100 unique tools and 512 KiB and follows discovery-event retention.
Incomplete/progressive catalogues without all schemas are never filled in from
later state. The training-context editor prefills retained catalogues but leaves
approval unchecked. The existing fingerprint, branch, timestamp, objective,
per-call review and task-consent gates still apply before dataset export.

Enable `MCPHUB_DATASET_BUILDER_ENABLED=true` explicitly. The default is disabled.

Each download now commits an export receipt and split registry before returning
bytes. `GET /api/datasets/exports?keyId=...` lists the latest 50 receipts for the
authenticated owner and exact key scope; the dashboard exposes this history.
Receipts retain source IDs, manifest, actual file SHA-256 and byte count, not JSONL
payloads or RAW. An interrupted network delivery may still have a receipt; it
proves committed generation, not successful delivery to the browser.

Within one owner/key scope, task, trace and duplicate-example fingerprints retain
their first exported split across seeds and selections. Duplicate source tasks
retain their linkage even when only one example is emitted. Export transactions
serialize per scope. A newly observed bridge between two different prior splits
returns 409 instead of moving previously exported data. Preview consults the same
registry without reserving assignments; concurrent exports may change a preview.
The registry stores hashed linkage tokens and outlives result retention to avoid
reintroducing leakage. It covers exports recorded after this feature was enabled;
older external files cannot be retroactively inferred or audited. Export receipts
are synchronous; background jobs and complete original client conversations remain pending.
Admin `POST /api/datasets/preview` and `/api/datasets/export` accept:

```json
{"resultIds":["RESULT_UUID"],"keyId":null,"allowSelfReported":false,
 "seed":"mcphub-v1","format":"tool-selection-sft","split":"train"}
```

Select 1–100 result IDs. Ownership always comes from the authenticated username;
`keyId` selects one of that owner's call scopes. A missing or foreign result is
reported identically as unavailable/out of scope. No cross-owner/key dataset is
assembled. Every preview and export re-reads the latest reviews and consent.

An example needs retained payload and digest, reviewed correct tool choice,
digest-bound privacy approval, reviewed discovery/task context, explicit task
consent and a user-confirmed positive/partial task outcome. Default attribution
requires trusted call-bound gateway/host evidence without conflicts. Self-reports
need separate explicit opt-in and remain labeled unverified. Unknown models,
incorrect calls, conflicts and revoked reviews cannot become positive examples.
Known credential patterns, sensitive argument values and email addresses are
excluded even when approval was recorded. This is a conservative detection pass,
not a complete PII detector; human privacy review remains required. Excluded
material is not silently rewritten into a different supposedly correct call.

Preview returns a versioned manifest with exclusion counts, deduplication count,
split sizes, seed and content digest. Export requires one split (`train`,
`validation`, `test`) and downloads JSONL, capped at 10 MiB. Responses are no-store.
Connected components of shared task IDs, trace IDs and duplicate input examples
are assigned together before the 80/10/10 split. Exact semantic input duplicates
are emitted once. Recorded prior assignments take precedence over a new seed.

Version 1 is explicitly **derived direct tool-selection SFT**: objective and
discovered catalogue are the prompt, reviewed backend tool/arguments are the
target. This normalizes the Smart facade into a direct tool-selection action;
it does not claim to reconstruct the original client's entire conversation.
Metadata preserves per-call model/segment, review revisions, task outcome and RAW
digest/result ID. RAW contents, trace keys, fictional final answers and automatic
training are excluded. DPO and full trajectories are not implemented by this
SFT format; execution success/failure alone never creates preference labels.

The separate `format: "recorded-tool-trajectory"` exports recorded tool events by
task/trace/branch/model segment. Select **every currently retained call** in each
segment; omitted, unreviewed, privacy-revoked or identity-conflicted calls exclude
the whole segment rather than silently creating a partial success story. Each
segment must have one known model. Trusted attribution remains the default and
explicit self-report opt-in remains labeled unverified. Reviewed task outcomes
may include failure; reviewed incorrect calls retain their quality and technical
execution labels. This is observational trajectory data, not positive-only SFT.

Events preserve objectives, available catalogues, actions, timestamps, review
revisions, per-call identity provenance and result ID/digest references. No RAW
contents, hidden client messages or final answers are reconstructed. Equal
timestamps do not prove causal order. Coverage explicitly means all **currently
retained** segment calls: old pruned events and original conversation completeness
remain unknown. Separate segments are exported separately and share task/trace
split constraints, including the same persistent registry used for SFT. The
dashboard format selector invalidates an old preview when changed.

### Explicit tool-preference DPO

`MCPHUB_DPO_ENABLED=true` is an additional default-off gate. The History dataset
panel can review two selected calls as a preference draft. Admin
`POST /api/datasets/preferences` accepts `chosenId`, `rejectedId`, `rationale`,
`comparabilityConfirmed: true`, optional `keyId` and explicit `allowSelfReported`.
The objective and ordered available catalogue must match canonically, actions
must differ, chosen call quality must be reviewed correct and rejected quality
reviewed incorrect. Both calls need current privacy/context approval, task consent
and trusted attribution by default. Chosen task outcome must be success/partial;
the rejected task can have a reviewed failure outcome. HTTP status does not create
a preference. The reviewer must compare relevant environment and tool-version
conditions; equality of text alone does not prove these conditions match.

Creation always saves a draft with privacy approval off. `PATCH
/api/datasets/preferences/:id` uses optimistic `revision` and `status`. Approval
requires separate `comparabilityConfirmed: true` and `privacyApproved: true`
against the exact saved revision, without editing rationale in that request.
Any changed source review or digest blocks approval/export. Refreshing as draft
rechecks current evidence, updates its snapshot and removes approval; review the
new revision before approving again. Retired labels remain in the audit and cannot
be revived; a replacement may be created. One active label per result pair and
canonical action comparison prevents duplicate or opposing current labels.
`GET /api/datasets/preferences?keyId=...` lists the latest 50 scoped labels.

Select both source calls and use `format: "tool-preference-dpo"` in the existing
preview/export endpoints. Up to 100 approved pairs are evaluated per selection.
The JSONL contains prompt/catalogue and chosen/rejected normalized tool actions,
separate source model/segment/review provenance, label revision and
`labelSource: "user_confirmed"`. Reviewer rationale is not exported. The context
is explicitly a **reviewed derived objective and catalogue**, not a verified copy
of hidden client conversation. No provider-verified preference is claimed.
Both sides and duplicate comparisons share persistent split constraints with SFT
and trajectories. Revocation/review changes exclude a previously approved pair;
old downloaded files cannot be recalled and should not be mixed with replacement
labels without rebuilding the dataset. There is no automatic fine-tuning.

Select results with the history table checkboxes to open the Dataset Builder
panel. It checks feature availability, offers the key scope and separate
self-report opt-in, previews eligibility/exclusion reasons, and downloads one
split. Changing selection or options invalidates the displayed preview. A stale
consent that leaves no eligible examples prompts a fresh preview instead of
saving an empty file. `GET /api/datasets/available` is admin-only.

Downloaded files cannot be recalled after consent withdrawal. Subsequent exports
re-check current consent rather than serving an old cached artifact. Persisted
dataset jobs remain subsequent work.
