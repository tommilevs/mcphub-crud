---

title: Model attribution
description: Optional task correlation and self-reported model identity
---

Enable the initial compatible implementation with `MCPHUB_ATTRIBUTION_MODE=compatible`.
The default is off. Existing calls remain valid without `hub_context`.
Alternatively, enable Model attribution in Smart Routing settings. Context lifetime
defaults to 168 hours and accepts 1–8760 hours. `MCPHUB_ATTRIBUTION_MODE` and
`MCPHUB_ATTRIBUTION_TTL_HOURS` override saved settings. Lifetime changes apply
to newly issued keys; existing keys retain their original expiry.

An authenticated caller can start correlation on any Smart Routing tool:

```json
{"query":"diagnose service","hub_context":{"action":"start","model_claim":"exact-model-id"}}
```

Omit `model_claim` when the exact identifier is unknown. The result keeps its
original content and adds `_meta["dev.mcphub/context"]` with server-generated
context, task, trace and model segment IDs. A newly issued context also includes
`trace_key`. Pass that key in later calls:

```json
{"toolName":"server-tool","arguments":{},"hub_context":{"trace_key":"k_RETURNED_KEY"}}
```

For an explicit model change, pass `action: "rotate"`, the current `trace_key`,
and the new `model_claim` (or omit it for an unknown model). Rotation preserves
task and trace, creates a fresh context/segment and key, and revokes the old key
in one PostgreSQL statement. Concurrent rotation allows only one successor.
Calls already running retain their original per-call snapshot.
Context creation, branch creation and model rotation also append a PostgreSQL
identity event in the same statement as the context mutation. Events contain
server identifiers, time and unverified model claims, with no raw correlation key.

Use `action: "fork"` with a current key to create a parallel branch of the same
task/trace. The parent key remains valid. The child receives its own branch,
segment and key; the parent's model and client claims are not inherited.
Optional `client_name_claim`, `client_instance_hint`, `agent_run_hint` and
`task_hint` on `start` are bounded unverified claims, stored separately from
server-generated identifiers. A task hint never becomes a server task ID.

Keys contain 192 random bits; PostgreSQL stores only SHA-256 digests. They expire
after seven days and are scoped to the authenticated username/API-key pair.
Keys correlate calls and grant no tool permissions. Missing, expired or foreign
keys do not block ordinary tool execution in compatible mode. They yield unknown
attribution. RAW tool results remain unchanged; history stores attribution in an
additional immutable JSON column with a unique call ID.

On authenticated attributed traffic, background maintenance removes up to 500
contexts whose expiry is more than 30 days old, at most once per hour per process.
Their lifecycle events cascade with them. Configure that post-expiry grace period
with `MCPHUB_ATTRIBUTION_RETENTION_DAYS` (1–3650). Cleanup does not delete tool
results or their immutable per-call attribution snapshots. No background timer is
kept alive; an idle hub defers cleanup until new attributed traffic arrives.

Model claims are always `self_reported` and `verified: false`. This implementation
does not detect models from IP addresses, model inventories or request timing.
Adapters may also send the correlation key in MCP request
`params._meta["dev.mcphub/attribution"].trace_key`. This is untrusted input:
`verified` flags are ignored. Conflicting keys or model claims yield unknown
per-call attribution with a conflict reason. Hub-owned metadata is removed before
upstream execution while unrelated request metadata is preserved.

Trusted host/gateway adapters,
identity analytics, training export gates and the settings UI are still pending.
Clients must be able to read MCP result metadata to retain the issued key.
An interrupted response can lose its newly issued key; start a new context to recover.

The Tool Results page includes an on-demand attribution summary of retained calls
from the last 30 days: known and verified coverage, conflicts, and up to 50
model/source observation groups with sample counts and execution-error counts.
Legacy results without attribution count as unknown. The admin endpoint
`GET /api/attribution/summary?days=30` accepts 1–3650 days. These observations
do not establish task success, tool-selection quality or a ranking of models.

Result metadata also includes a conservative `trainingReadiness` assessment,
shown in result details. It distinguishes trusted, unverified, unknown,
conflicted and excluded attribution, and lists missing consent, reviewed
outcome, discovery context, redaction review or available payload.
Verified host/gateway claims additionally require server-verified causal
correlation. Request metadata cannot supply these review gates. Until trusted
adapters and remaining per-call evidence are implemented, records remain ineligible for
model-specific training. This assessment does not export data or create SFT/DPO
examples, and successful tool execution never substitutes for an assessed outcome.

Administrators can explicitly review a task outcome and grant or withdraw training
permission in result details. `PUT /api/attribution/tasks/:taskId/review` accepts
`outcome` (`unknown`, `success`, `failure`, `partial`, `abandoned`), an explicit
boolean `trainingConsent`, and the current `revision` (0 for a first review).
Each change appends an auditable revision with reviewer and timestamp. Concurrent
or stale writes return 409. New tasks have no outcome assessment and no training
permission. The latest review applies across the task's results, without changing
RAW, attributing the whole outcome to a model, or marking each call as correct.

Attributed `search_tools` and `describe_tool` calls now record bounded discovery
evidence: visible candidate names and SHA-256 schema fingerprints (null when the
schema was not disclosed), linked to the actual call/trace/branch. The record
omits search text, tool descriptions and schema contents/defaults. At most 100
candidates are recorded and truncation is explicit. A telemetry failure leaves
the original response unchanged. Evidence follows context retention. Fingerprints
alone do not satisfy the full discovery-context training gate; a complete,
privacy-reviewed schema catalogue and task context are still required for SFT.

## Per-call review gates

Result details provide independent tool-choice/argument quality and privacy reviews.
`PUT /api/tool-results/:id/review` accepts `quality` (`unknown`, `correct`,
`incorrect`, `uncertain`), `privacy` (`unreviewed`, `approved`, `rejected`),
the previously observed `revision` (zero initially), and `rawSha256`.
Only admins may review. The digest must match the retained payload; unavailable
payloads and stale revisions cannot be approved. Reviews append audit revisions
and the latest review is returned with history. Result retention cascades reviews.

RAW is never rewritten. Privacy approval asserts a review of this call's original
payload, arguments and metadata; it does not perform redaction or permit use of
other calls. Rejection or returning to unreviewed status closes this gate again.
Task training consent, outcome review, complete discovery/task context and trusted
causal model provenance remain separate requirements. Correct/incorrect is an
explicit call assessment, not inferred from execution status or task success.
An incorrect call must not be used as a positive SFT demonstration merely because
its review is complete; dataset-specific selection still applies.

## Optional instrumented gateway adapter

`src/services/gatewayProvenance.ts` provides an instrumented OpenAI-compatible
gateway reference. `createGatewayProof` accepts the concrete provider response,
selects exactly one response tool-call ID and requires its function name and JSON
arguments to match the outgoing MCP invocation. The signed proof binds the
provider-reported model/response/tool-call IDs, invocation request ID and content
digest, authenticated-owner digest, timestamp and random nonce. JSON object key
order does not change the binding.

`verifyGatewayProof` requires an operator-trusted adapter key resolver and a
durable, atomic nonce-consumption callback. Proofs expire after 60 seconds, permit
at most five seconds of clock skew, and reject changed invocations, owners,
signatures, unknown adapters and replay. Keys must contain at least 32 characters
and must never be supplied by the model or stored in project files.

In compatible mode, attach the proof as MCP request `_meta["dev.mcphub/provenance"]`.
Register operator-trusted adapter IDs and secrets in `MCPHUB_GATEWAY_ADAPTER_KEYS`
(a JSON object mapping adapter IDs to secrets in the runtime environment). No
adapters are trusted by default. The owner used by the signer must match the
hub's authenticated principal, serialized as `[username-or-null,key-id-or-null]`.
Anonymous calls cannot establish verified provenance.

Runtime validates the original invocation before stripping hub metadata upstream.
MCP SDK v2 exposes the original JSON-RPC ID in the handler context (`mcpReq.id`),
not in the parsed request. The hub uses that transport ID for proof verification;
older handler contexts fall back to `requestId`. Arguments and the tool name
remain those of the parsed invocation.
PostgreSQL consumes each adapter/nonce pair once atomically across workers;
expired nonce cleanup is bounded. Valid evidence upgrades only the current call's
snapshot to `gateway_observed`; it does not upgrade stored correlation contexts
or later unsigned calls. Call ID remains unchanged. Conflicting claimed and
observed model IDs are both retained with an explicit conflict and excluded from
trusted training eligibility. Result details show adapter, response and tool-call
identifiers. The verified-coverage summary also requires causal evidence.

A reviewed deployment of the instrumented gateway is still required; no real
external gateway deployment has been verified by these implementation tests.
An HMAC proves that a trusted adapter signed the
correlation; it cannot independently prove the provider or a compromised adapter
truthful. Merely passing a configured model or attaching unsigned client metadata
must never upgrade attribution. Unsigned calls remain self-reported/unknown.
