---
title: Model attribution
description: Optional task correlation and self-reported model identity
---

Enable the initial compatible implementation with `MCPHUB_ATTRIBUTION_MODE=compatible`.
The default is off. Existing calls remain valid without `hub_context`.
Alternatively, enable Model attribution in Smart Routing settings. Context lifetime
defaults to 168 hours and accepts 1–8760 hours. `MCPHUB_ATTRIBUTION_MODE` and
`MCPHUB_ATTRIBUTION_TTL_HOURS` override saved settings. Lifetime changes apply
to newly issued keys; existing keys retain their original expiry.

An authenticated caller can start correlation on any Smart Routing tool:

```json
{"query":"diagnose service","hub_context":{"action":"start","model_claim":"exact-model-id"}}
```

Omit `model_claim` when the exact identifier is unknown. The result keeps its
original content and adds `_meta["dev.mcphub/context"]` with server-generated
context, task, trace and model segment IDs. A newly issued context also includes
`trace_key`. Pass that key in later calls:

```json
{"toolName":"server-tool","arguments":{},"hub_context":{"trace_key":"k_RETURNED_KEY"}}
```

For an explicit model change, pass `action: "rotate"`, the current `trace_key`,
and the new `model_claim` (or omit it for an unknown model). Rotation preserves
task and trace, creates a fresh context/segment and key, and revokes the old key
in one PostgreSQL statement. Concurrent rotation allows only one successor.
Calls already running retain their original per-call snapshot.
Context creation, branch creation and model rotation also append a PostgreSQL
identity event in the same statement as the context mutation. Events contain
server identifiers, time and unverified model claims, with no raw correlation key.

Use `action: "fork"` with a current key to create a parallel branch of the same
task/trace. The parent key remains valid. The child receives its own branch,
segment and key; the parent's model and client claims are not inherited.
Optional `client_name_claim`, `client_instance_hint`, `agent_run_hint` and
`task_hint` on `start` are bounded unverified claims, stored separately from
server-generated identifiers. A task hint never becomes a server task ID.

Keys contain 192 random bits; PostgreSQL stores only SHA-256 digests. They expire
after seven days and are scoped to the authenticated username/API-key pair.
Keys correlate calls and grant no tool permissions. Missing, expired or foreign
keys do not block ordinary tool execution in compatible mode. They yield unknown
attribution. RAW tool results remain unchanged; history stores attribution in an
additional immutable JSON column with a unique call ID.

On authenticated attributed traffic, background maintenance removes up to 500
contexts whose expiry is more than 30 days old, at most once per hour per process.
Their lifecycle events cascade with them. Configure that post-expiry grace period
with `MCPHUB_ATTRIBUTION_RETENTION_DAYS` (1–3650). Cleanup does not delete tool
results or their immutable per-call attribution snapshots. No background timer is
kept alive; an idle hub defers cleanup until new attributed traffic arrives.

Model claims are always `self_reported` and `verified: false`. This implementation
does not detect models from IP addresses, model inventories or request timing.
Adapters may also send the correlation key in MCP request
`params._meta["dev.mcphub/attribution"].trace_key`. This is untrusted input:
`verified` flags are ignored. Conflicting keys or model claims yield unknown
per-call attribution with a conflict reason. Hub-owned metadata is removed before
upstream execution while unrelated request metadata is preserved.

Trusted host/gateway adapters,
identity analytics, training export gates and the settings UI are still pending.
Clients must be able to read MCP result metadata to retain the issued key.
An interrupted response can lose its newly issued key; start a new context to recover.

The Tool Results page includes an on-demand attribution summary of retained calls
from the last 30 days: known and verified coverage, conflicts, and up to 50
model/source observation groups with sample counts and execution-error counts.
Legacy results without attribution count as unknown. The admin endpoint
`GET /api/attribution/summary?days=30` accepts 1–3650 days. These observations
do not establish task success, tool-selection quality or a ranking of models.

Result metadata also includes a conservative `trainingReadiness` assessment,
shown in result details. It distinguishes trusted, unverified, unknown,
conflicted and excluded attribution, and lists missing consent, reviewed
outcome, discovery context, redaction review or available payload.
Verified host/gateway claims additionally require server-verified causal
correlation. Request metadata cannot supply these review gates. Until persisted
reviews and trusted adapters are implemented, records remain ineligible for
model-specific training. This assessment does not export data or create SFT/DPO
examples, and successful tool execution never substitutes for an assessed outcome.
